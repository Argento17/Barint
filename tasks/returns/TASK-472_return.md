## Root-cause / contract check (why I did NOT touch `ingredients_list`)

Before writing anything, I traced how `bsip1_source_path` and `ingredient_list` are actually produced by the BSIP2 engine, to avoid inventing a value the engine itself never computes:

- `03_operations/bsip2/proto_v0/src/input_loader.py::load_batch()` sets `data["_source_path"] = str(path)` to the literal glob'd file path of the BSIP1 JSON it loaded — this is exactly what ends up in the trace's `input_reference.bsip1_source_path` field. Verified against a **working, non-null example** (`02_products/bread_light/.../bsip1_bread_light_9990001000001/bsip2_trace.json` → `bsip1_source_path` = the real file path of `03_operations/bsip1/run_bread_light_001/output/bsip1_9990001000001.json`).
- `input_loader.py::get_ingredients()` returns `product.get("ingredients_list") or []` — i.e. the trace's `L1_observed_signals.ingredient_list` (and its L3 copy) is a **mechanical, verbatim pass-through of BSIP1's own `ingredients_list` field**, never derived from `ingredient_order`. Verified byte-for-byte on the same bread_light example: `trace.L1.ingredient_list == bsip1_file.ingredients_list` → `True`, and same for L3.
- Every crackers BSIP1 file (`bsip1_<barcode>.json`, all 20) has `"ingredients_list": []` — confirmed by direct read. The real ingredient data lives in `ingredients_raw` / `ingredients_text_he` (full string) and `ingredient_order` (structured, position-ordered objects with `text`/`percentage_declared`/`has_subgroup`) — populated via `ingredients_raw_provenance.source: "bsip1_text_fallback"` (BSIP0 was unavailable; BSIP1 used its text fallback, see `data_fixes_applied`).

**Conclusion:** the trace's `ingredient_list: []` is the *correct, faithful* output of the engine given its actual upstream input — not a broken/missing repair item. Populating it from `ingredient_order` would deviate from the documented mechanical contract that every other category in this codebase follows (I could not find a single trace anywhere in the repo where `ingredient_list` is anything other than a direct copy of BSIP1's `ingredients_list`). Per the task's own fallback instruction ("If the field's contract is ambiguous or no faithful source exists, LEAVE IT and report it — do not fabricate"), I left `ingredient_list` untouched in all 20 files and am reporting this here rather than silently complying with step 3's literal wording, which would have introduced a value with no engine precedent.

**Spec-conflict flag (per Spec-Conflict Duty):** step 2.3 of the task instructs deriving `ingredients_list` from `ingredient_order`/`ingredients_text_he` "if the field's contract is the parsed ingredient list." I determined the contract (via `input_loader.get_ingredients()`) is **pass-through of BSIP1's own `ingredients_list`**, not an independent BSIP2-side derivation from `ingredient_order`. Since BSIP1's own `ingredients_list` is `[]` for all 20 crackers records, "faithful" repair at the BSIP2-trace layer means leaving it `[]` — matching what the engine would produce on a fresh run. If the fix intended is "backfill BSIP1's `ingredients_list` field itself from `ingredient_order`, then let the pass-through carry it forward," that is a **different, larger change** (touches 20 BSIP1 corpus files, is a BSIP1-schema decision, and arguably is enrichment work, not audit-trail repair) — flagging it for Product/Nutrition Agent judgment rather than doing it unilaterally under an audit-trail-only mandate.
